# Accounts, Recipe Book and Preferences Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Visitors can sign in with email + password or Google, keep a recipe book of generated and hearted recipes that follows them between devices, and save preferences that Claude follows when it writes a new recipe.

**Architecture:** Supabase Auth in the existing project, reached from the browser with `@supabase/supabase-js` served from the site and loaded only for signed-in visitors and on the account pages. New tables behind row level security hold profiles and the recipe book; `generate-recipe` accepts an optional sign-in. The existing plain scripts keep drawing hearts from `localStorage`; one new module (`account.js`) keeps that copy in step with the account.

**Tech Stack:** Eleventy 3.1.7, Nunjucks, plain browser scripts and ES modules (no bundler), Supabase (Auth, Postgres with RLS, Edge Functions on Deno), `node --test` on Node 24.

**Spec:** `docs/superpowers/specs/2026-11-12-accounts-design.md`. Read it and `HANDOFF.md` before starting.

## Global Constraints

- Site copy is Swedish; replies to the owner are English. The site is called **Ofta bra efter**. New internal names keep the existing `restfest` prefix (storage keys, events, meta names), as HANDOFF's "The name" explains.
- Every Swedish string in this plan is a draft. Task 8 collects all new copy for the owner's approval.
- No framework, no bundler. Every template in `src/pages/` sets its own `permalink:`. New pages are `noindex`, except `integritet.html`.
- Only the publishable key may reach the browser. Nothing here may need a paid Supabase plan.
- While `ai.accounts` is false (project address or publishable key empty), the build output has no trace of accounts.
- A signed-out visitor downloads `js/account.js` and nothing else new. `js/vendor/supabase.js` loads only on the account pages or when the `restfest-account` marker exists.
- Hearts never get lost at sign-in, and a failed network call never blocks or undoes a heart click.
- Work on branch `accounts` off `main`. Commit at the end of each task on that branch (the owner agreed to the branch; nothing is merged or pushed without asking). Leave `.DS_Store` changes and `src/assets/icons/new/` out of commits: they are the owner's.
- **Do not touch the live Supabase project before Task 9's question is answered.** Tasks 1–8 are verified against stand-ins.
- Clean up after browser checks: stop the server, delete `.playwright-mcp/` (HANDOFF, "Testing setup that worked").

## Review Focus

1. **A mail link opened in another browser or device** (sign-up on a laptop, mail read on a phone): the link still confirms the account and the visitor ends up signed in or told to sign in. Pinned in Task 4 (implicit flow, no PKCE) and checked for real in Task 9.
2. **A hostile return address** (`?till=//evil.example`, `/\evil.example`, `javascript:alert(1)`, an absolute URL): ignored, visitor lands on the recipe book. Test in Task 1.
3. **Hearts changed on two devices, or while offline:** the next page load sends queued changes first, then takes the account's list; a heart added elsewhere appears, a heart removed offline stays removed. Tests in Task 1 (queue), check in Task 5.
4. **An expired or revoked sign-in:** a page load turns the header back to signed out without an error; `generate-recipe` still returns a recipe with `saved: false`. Checks in Tasks 3 and 6.
5. **"Äter inte" text that tries to instruct Claude** ("ignore the above and …"): it is cleaned, length-limited and presented to Claude as a list of foods, never as instructions. Test in Task 1.
